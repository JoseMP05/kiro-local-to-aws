03 · Arquitectura objetivo

Lo que Kiro debería proponer

Es la arquitectura de la solución de referencia (infra/ en la rama referencia-aws). Sirve para contrastar lo que proponga Kiro en vivo. Cada decisión sale del contrato de despliegue del README.

Una sola tarea, también al desplegarEl estado vive en memoria. desiredCount 1, minHealthyPercent 0 y maxHealthyPercent 100: nunca hay dos partidas a la vez.
CloudFront delanteHTTPS sin dominio ni certificado propio. El cliente cambia solo a wss://. Política sin caché y reenvío de todas las cabeceras para el WebSocket.
ALB cerrado a CloudFrontEl security group solo admite la prefix list administrada com.amazonaws.global.cloudfront.origin-facing.
Despliegues rápidosEl servidor se apaga en menos de 3 s, así que el deregistration delay baja de 300 s a 5 s. Health check cada 10 s sobre /health.
Sin NAT GatewayLa tarea vive en subred pública con IP pública para bajar la imagen de ECR. Ahorra unos 32 USD al mes.
x86_64La imagen se construye en el portátil (x86). Evita sorpresas de emulación ARM en directo.
ServicioPara quéPor qué este y no otroCosto aprox.
ECS FargateEjecutar el contenedor del juegoContenedores sin administrar servidores. Soporta procesos largos y WebSocket, a diferencia de Lambda.~1,20 USD/día
Application Load BalancerHealth check, IP estable para CloudFrontSoporta WebSocket de forma nativa y reemplaza la tarea si deja de responder.~0,55 USD/día
CloudFrontHTTPS público y borde globalCertificado gratuito sin dominio; soporta WebSocket. 1 TB/mes gratis.~0 en charla
ECRGuardar la imagen DockerCDK la construye y la sube en el mismo cdk deploy.céntimos
CloudWatch LogsVer la salida del servidorDiagnóstico en vivo con aws logs tail.céntimos
VPC + IPv4 públicasRed aisladaSin NAT. Se pagan las IPv4 públicas del ALB y de la tarea.~0,36 USD/día
Alternativas que Kiro puede proponer y cómo responder

Lambda + API Gateway WebSocket. Obligaría a reescribir el servidor: el bucle de ticks a 30 Hz y el estado en memoria no encajan en funciones efímeras.

App Runner. No admite conexiones WebSocket, que el juego necesita.

EC2 con Docker. Más barato, pero hay que parchear el sistema operativo y montar el reinicio automático a mano.

ECS Express Mode. Crea el ALB y la URL HTTPS solo, y es una buena variante para comparar. Verifica que deje fijar una única tarea antes de usarlo en directo.

Varias réplicas con autoescalado. Rompe el juego: cada réplica sería una partida distinta. Hace falta estado compartido (por ejemplo ElastiCache) y es otra charla.

04 · Kiro en modo SDD

Los prompts, en orden

Cada paso indica dónde escribirlo en Kiro, el texto exacto para copiar y qué revisar antes de aprobar. Kiro genera los tres archivos de la spec en .kiro/specs/aws-infra/ y pide aprobación entre fases: es el momento de leerlos en voz alta con el público.

preparación

Dónde: panel de Kiro → Steering → Generate Steering Docs. Crea .kiro/steering/product.md, tech.md y structure.md, que Kiro lee en cada conversación.

MCP de documentación de AWS: en .kiro/settings/mcp.json añade el servidor remoto AWS Knowledge para que Kiro consulte documentación oficial en lugar de recordar de memoria.

      "disabled": false
    }
  }
}

1Analizar el juego

min 20 · ~2 min

Dónde: chat de Kiro, sesión Vibe. Solo lectura: no crea archivos.

Prompt
Analiza este repositorio antes de proponer nada. Quiero llevar el juego de tanques a AWS.

Lee el README (en especial la sección "Contrato de despliegue"), el Dockerfile, src/server/start.js y config.json, y resúmeme en una lista corta:
- cómo se ejecuta el servidor y en qué puerto,
- qué protocolos usa (HTTP, WebSocket) y en qué rutas,
- dónde vive el estado de la partida y qué implica para escalar,
- qué ofrece para health check y apagado ordenado,
- qué recursos (CPU, ancho de banda) necesita con 100 jugadores.

No escribas código ni crees archivos todavía.
Qué revisar
  • Detecta una sola réplica por el estado en memoria.
  • Ve HTTP y WebSocket en el mismo puerto (/ws/jugador, /ws/espectador).
  • Menciona /health, SIGTERM y el ping cada 10 s.
Qué decir al público

“Antes de pedir infraestructura, le pedimos que entienda la aplicación. Todo lo que necesita está en el README porque lo dejamos escrito en la spec anterior.”

2Crear la spec: requisitos

min 22 · ~4 min

Dónde: chat de Kiro → nueva sesión Spec (o el botón + en el panel Specs). Nombre sugerido: aws-infra. Kiro escribe requirements.md en formato EARS.

Prompt
Crea una spec llamada aws-infra para desplegar este juego en AWS. Continúa la spec online-readiness, que dejó el despliegue en AWS fuera de su alcance. Escribe los documentos en español, como las specs que ya existen en .kiro/specs/.

Objetivo: que cualquier persona del público abra una URL pública con HTTPS desde el móvil y juegue, y que el proyector muestre /espectador.

Restricciones (salen del Contrato de despliegue del README):
- Una sola instancia del servidor en todo momento, también durante un despliegue: dos instancias serían dos partidas.
- HTTP y WebSocket por el mismo puerto; el WebSocket debe funcionar por HTTPS (wss://).
- Usar /health como health check y respetar el apagado ordenado con SIGTERM.
- Usar el Dockerfile que ya existe; no modificar el código del juego.
- Región us-east-1, cuenta ya inicializada con CDK.
- Infraestructura como código con AWS CDK en TypeScript dentro de una carpeta infra/.
- El stack se llama TankGameLive.
- Sin dominio propio: la URL puede ser la que da AWS.
- Costo bajo mientras no hay charla, y se tiene que poder borrar todo con un solo comando.
- Logs del servidor accesibles desde la consola o la CLI.

Empieza solo por requirements.md.
Qué revisar antes de aprobar
  • Hay un requisito explícito de “nunca dos tareas a la vez”.
  • WebSocket sobre HTTPS aparece como criterio verificable.
  • Hay requisito de salidas: URL del juego, espectador y health.
  • Hay requisito de borrado completo (cdk destroy).
Si falta algo, pídelo así
Ajuste
Añade dos requisitos: el balanceador solo debe aceptar tráfico que venga de la CDN, y un despliegue nuevo debe tardar poco en drenar conexiones porque el servidor se apaga en menos de 3 segundos.

3Diseño: proponer y explicar la arquitectura

min 26 · ~5 min

Dónde: misma sesión Spec, después de aprobar los requisitos. Kiro escribe design.md.

Prompt
Requisitos aprobados. Ahora el design.md:

1. Compara al menos tres opciones de cómputo en AWS para este juego (por ejemplo ECS Fargate, EC2, App Runner, Lambda con API Gateway WebSocket) en una tabla: soporte de WebSocket, estado en memoria, esfuerzo de operación y costo mensual aproximado. Elige una y justifica.
2. Incluye un diagrama Mermaid de la arquitectura final con el recorrido de una conexión WebSocket desde el navegador hasta el contenedor.
3. Explica cada servicio elegido en una o dos frases, pensando en un público que no conoce AWS.
4. Detalla las decisiones de configuración que salen de los requisitos: número de tareas y porcentajes de despliegue, health check, timeouts, seguridad de red y política de caché de la CDN.
5. Añade una estimación de costo por día con el entorno encendido y sin jugadores.

Consulta la documentación de AWS si tienes la herramienta disponible.
Qué revisar
  • Descarta App Runner y Lambda por WebSocket o estado.
  • minHealthyPercent 0 / maxHealthyPercent 100.
  • CloudFront con CachingDisabled y AllViewer.
  • Security group del ALB con la prefix list de CloudFront.
  • Deregistration delay corto (5–10 s).
Si propone algo distinto

Compáralo con la arquitectura objetivo. Si es viable (por ejemplo ECS Express Mode), puede ser un buen momento de debate. Si rompe la réplica única o el WebSocket, usa el ajuste:

Ajuste
Revisa el diseño contra el requisito de una sola instancia y WebSocket por HTTPS. Usa CloudFront delante de un Application Load Balancer y una única tarea de ECS Fargate, sin NAT Gateway.

4Plan de tareas

min 31 · ~2 min

Dónde: misma sesión Spec. Kiro escribe tasks.md con casillas y referencias a los requisitos.

Prompt
Diseño aprobado. Genera tasks.md con tareas pequeñas y verificables, cada una con los requisitos que cubre:
- crear el proyecto CDK en infra/ (TypeScript, sin tocar el resto del repo),
- red, balanceador, servicio de contenedores y CDN, cada uno en su tarea,
- salidas del stack con las URL del juego, del espectador y de /health,
- validar con cdk synth,
- desplegar con cdk deploy,
- verificar /health, el juego y el WebSocket con la URL pública,
- documentar en el README cómo desplegar y cómo destruir.

No marques como opcionales las tareas de despliegue y verificación.

06 · PRs del público

De un PR a producción, solo

El repositorio revisa y despliega sin intervención: cada PR recibe pruebas y una revisión automática en español, y cada merge a main actualiza el entorno de la charla. GitHub Actions entra a AWS con OIDC, sin claves guardadas.

CuándoWorkflowQué hacePermisos en AWS
Se abre o actualiza un PRci.ymlpnpm test con Node 24. Corre también para forks.Ninguno
Se abre o actualiza un PRpr-review.ymlLee el diff por la API (nunca ejecuta el código del PR), lo revisa con Claude Haiku en Amazon Bedrock contra .github/pr-review-guidelines.md y deja un veredicto y comentarios en las líneas. Unos 30 s por PR.Rol tank-game-gh-pr-review: solo invocar Claude Haiku
Merge a maindeploy.ymlPruebas, cdk deploy y comprobación de /health. Si main ya tiene la infra/ de Kiro despliega TankGameLive; si no, TankGameRef con la infra de la rama referencia-aws.Rol tank-game-gh-deploy: solo desde main, solo roles de CDK
En el escenario
  • Proyecta el repositorio en GitHub y pide a alguien que abra un PR pequeño (por ejemplo, un efecto nuevo a partir de src/effects/builtin/turbo.js).
  • A los pocos segundos aparecen las pruebas y la revisión automática con sus comentarios.
  • Fusiona el PR y abre la pestaña Actions: el despliegue tarda unos 3 minutos.
  • Avisa antes de fusionar: con una sola tarea, la partida se corta 30–60 s mientras arranca la versión nueva.
AWS DevOps Agent (opcional)

Su revisión release readiness también comenta PRs, pero el disparo automático solo funciona en repositorios privados. En este repositorio público se puede mostrar bajo demanda: en su consola, pide la revisión del PR por número. Tarda 8–10 minutos, así que lánzala al empezar este bloque.

08 · Después de la charla

Limpieza y costos

Con el entorno encendido y sin jugadores, cada stack cuesta unos 2 USD al día (Fargate, ALB e IPv4 públicas). Con 100 jugadores, el juego envía unos 110 KiB/s a cada uno: unos 40 GB por hora de partida, cubiertos por el TB gratuito mensual de CloudFront. Borra los dos stacks al terminar.

Borrar todo
cd infra && npx cdk destroy TankGameLive --force      # el de Kiro (rama main)
git switch referencia-aws && cd infra && npx cdk destroy TankGameRef --force
npx cdk destroy TankGameCi --force                    # roles de GitHub Actions

El stack CDKToolkit puede quedarse: no cuesta casi nada y evita repetir el bootstrap en la próxima charla.
